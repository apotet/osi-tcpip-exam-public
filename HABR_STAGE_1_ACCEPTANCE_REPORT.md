## Решение о приёмке

**Автоматическая часть аудита пройдена в описанном ниже объёме. Полная приёмка
Habr Stage 1 остаётся открытой.** Оснований объявить v1.0 Habr-ready или дать
безусловную рекомендацию merge в `main` пока недостаточно: не закрыты ручная
проверка реальных браузеров и устройств, техническая редактура банка и проверка
содержимого CLI.

Рекомендация для этой ветки: рассматривать её как аудит и ограниченные исправления.
Перед merge выполнить список проверок в конце отчёта. Успешный merge этой ветки
сам по себе не закрывает критерий Habr-ready из [исходного чек-листа](HABR_READY_AUDIT.md).
Это инженерная оценка по имеющимся свидетельствам, а не выполненное действие merge.

на 360, 390, 430 и 1440 px. Быстрые клики подготовки оставляли учебные карточки
закрытыми. Подготовка заменена на `details.open` с проверкой открытого состояния.
После этого повторены все 15 сочетаний OSI-сценария: **15/15 pass**.
Итоговая сводка объединяет последний результат каждого уникального сценария;
это **не один непрерывный полный прогон с 135 pass**.

Позже исправлен favicon и отдельно выполнены 15 проверок страниц/иконок.
Полная матрица после последнего изменения HTML не повторялась. Перед merge нужен
один полный прогон на окончательном кандидате с текущей подготовкой тестов.
Изначальные таймауты не доказывают дефект продукта, но их обход через DOM
не доказывает исправность реальных кликов по summary — это отдельная ручная проверка.

## Ограничения автоматических тестов

- Linux WebKit не эквивалентен Safari на iOS. Chromium не подтверждает все
  особенности брендированного Chrome; Firefox проверен только в Linux/headless.
- Учебные и CLI-карточки открываются программно. Кнопки диалогов нажимаются
  через Playwright, но цепочка реальных касаний по summary не проверяется.
  Условие «все detail непустые» не сравнивает содержимое с правильным вендором.
- 135 — число сочетаний девяти тестов и пятнадцати конфигураций, а не покрытие
  всех вопросов, ветвей кода или вариантов поведения. Банк загружается целиком,
  но все 343 вопроса в интерфейсе не предъявляются и не проверяются.
- Выбор первого ответа и ввод `1` подтверждают работу переходов и feedback;
  тесты не утверждают правильность ответа, explanation, итогового счёта или зачёта.
  Для OSI нет целевого сценария multiple choice с выбором всех правильных ответов.
- Проверка overflow относится к ширине корневого документа с допуском 1 px.
  Она не проверяет перекрытия, обрезку каждого элемента, высоту модалки,
  экранную клавиатуру или читаемость. Скриншоты не сравниваются с эталоном;
  `cli/read.html` снимается только в пределах viewport из-за лимита Firefox.
- Перехватываются ошибки в посещённых состояниях; отсутствие ошибок там
  не доказывает отсутствие null/undefined или обращений к отсутствующим DOM
  во всех ветвях. `console.warn` не является условием падения. Confirm автоматически
  принимается — сценарий отмены не выполняется.
- Проверка ссылок ограничена собранными href/src и фото банка. Fragment ID
  ищется в HTML как строка; успешный HTTP не доказывает удобство реального перехода.
  Внешние ссылки на документацию и лицензии этим обходом не проверялись.
- Проверка банка подтверждает структуру индексов correct, а не истинность ответа.
  Точные текстовые дубли собираются в отчёт, но их наличие само по себе не вызывает
  assert в текущем `static.cjs`; near-duplicate review проводился отдельно.
- IPv4-сравнение network/broadcast/first/last ограничено /8–/30. /0–/7, /31, /32
  проверены только как маски в этом автоматическом расчётном наборе. Для VLSM
  проверены задания текущего генератора, а не произвольное распределение подсетей.
- Seed зафиксирован для IPv4/VLSM. Выборки QuizEngine и случайные задания UI
  используют Math.random без фиксированного seed; повторный прогон может выбрать
  другой набор вопросов. Функции IPv4 извлекаются из HTML по строковым границам;
  это не проверка всех обработчиков ввода и зависимостей страницы.
- Поиск мёртвого кода по числу вхождений именованных функций — эвристика;
  не анализируются все экспорты, динамические вызовы, анонимные функции и CSS.
  Размеры, SHA-256 и ссылочные проверки не являются проверкой лицензий.
- В текущем окружении WebKit использовал копию wrapper и библиотеки в `/tmp`;
  отключена проверка host requirements через ldconfig, сам движок работал.
  Запуск стандартной установки в чистом окружении отдельно не подтверждён.
- Raw JSON, скриншоты и traces сохранены локально и исключены из git. В репозитории
  есть компактные сводки, но нет настроенного workflow `.github` и автоматического
  сохранения этих артефактов в CI. `npm test` запускает static + browser;
  дополнительные links/resources/icons вызываются отдельно.

Приоритеты ниже относятся к пробелам проверки, а не к новым обнаруженным дефектам.

| Риск | Приоритет | Что нужно для снижения риска |
|---|---|---|

| Реальные касания, Safari/Android, клавиатура и viewer могут вести себя иначе | Высокий для пользовательской приёмки | Регрессия текущего кандидата на реальных iPhone/Android с явными кликами по карточкам; протокол проверки |
| DOM-подготовка устраняет таймаут теста, но может скрыть проблему пользовательского открытия карточек | Средний | Проверить реальные клики L1–L7 и длинных CLI-summary; исходные traces сохранить для сравнения |
| Сводка объединяет прогоны; последний HTML с favicon не прошёл заново все 135 сценариев | Средний | Один полный успешный прогон на окончательном кандидате; отдельные checks links/resources/icons; сохранить артефакты |
| Не проверены итоговый счёт, positive cases, состояние хранения и независимая арифметика IPv6 | Средний | Контрольные ручные сценарии с заранее известными ответами и ожидаемой статистикой; отдельно IPv6 |
| Localhost и существующая публичная версия не подтверждают публикацию audit-кандидата и скорость загрузки | Средний | Preview/публикационная проверка кандидата под реальным base path и на мобильной сети; измерить загрузку |
| Результаты трудно повторно проверить вне текущего окружения; ветка локальная | Средний | Стандартная установка зависимостей, полный прогон и сохранение raw-артефактов; сопоставить diff с актуальным main при подготовке merge |

Отсутствие конфликтов с актуальным удалённым `main` здесь не проверялось:
при подготовке отчёта fetch/rebase/merge и публикация ветки не выполнялись.
Если `main` является источником GitHub Pages, merge может сразу изменить публичный
сайт; порядок публикации нужно учесть при проверке кандидата.
